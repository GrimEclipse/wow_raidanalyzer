# Feature Specification: S2 大秘境关键技能筛选（S2 Mythic Key Skills）

**Feature Branch**: `speckit/s2-key-skills`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: 将 `/mythic-dungeon` S2 页面从「实际施法候选」预览升级为经过筛选的关键技能判定：从候选施法中区分 Boss 关键技能与小怪施法，形成可维护的 S2 关键技能清单。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看已判定的 S2 关键技能清单 (Priority: P1)

团长打开 `/mythic-dungeon`，选择一份 S2 样本日志，页面在「实际施法候选」之外明确展示哪些敌方施法已被判定为关键技能、哪些被判定为小怪施法/可忽略，两类泾渭分明，不再是一锅端的长列表。

**Why this priority**: 这是本特性的核心价值——把「预览」变成「结论」，团长复盘时直接看结论。

**Independent Test**: 导入一份 S2 样本 JSON 后，页面出现关键技能与小怪施法两个分组，且分组内条目与后端判定数据一致。

**Acceptance Scenarios**:

1. **Given** 一份含敌方施法记录的 S2 样本, **When** 页面加载完成, **Then** 候选施法被分为「关键技能」与「小怪/其他」两组展示，每组带技能名与出现次数。
2. **Given** 某技能已被判定, **When** 页面渲染, **Then** 判定结果持久可见（刷新后不变），不随页面会话丢失。

### User Story 2 - 关键技能判定有据可查 (Priority: P2)

团长或维护者想核实某个技能为什么被判为关键技能：每个判定附带依据（伤害/治疗量阈值命中、光环影响、官方机制来源等），可以在页面上展开查看，数据与判定规则同源。

**Why this priority**: 判定可信度决定这份清单敢不敢用；没有依据的清单会被怀疑。

**Independent Test**: 点击任一已判定技能，能看到结构化的判定依据字段，且依据内容与该样本的实际证据对应。

**Acceptance Scenarios**:

1. **Given** 一个被判为关键的技能, **When** 展开其详情, **Then** 显示至少一类量化依据（伤害总量/受影响玩家数/出现场次）。
2. **Given** 判定数据文件, **When** 检查其内容, **Then** 每条判定包含 `evidence` 字段或等价结构，无凭空判定的条目。

### User Story 3 - 维护者可增量修订清单 (Priority: P3)

维护者后续核对更多日志后，能通过编辑一份声明式数据文件（清单）增删改判定，无需改动前端或通用运行时代码；页面下一次加载即反映新判定。

**Why this priority**: S2 样本与机制认识会持续演进，判定必须是数据驱动而非代码硬编码。

**Independent Test**: 修改判定数据文件中一条技能的分类后刷新页面，展示随之变化，全程未改任何 JS/通用 Python 代码。

**Acceptance Scenarios**:

1. **Given** 判定数据文件中某技能从「小怪」改为「关键」, **When** 页面重新加载, **Then** 该技能出现在关键技能分组。
2. **Given** 判定数据文件格式错误（JSON 解析失败）, **When** 页面加载, **Then** 服务不崩溃，页面回退展示「实际施法候选」原始行为并提示判定数据不可用。

## Edge Cases

- 样本中敌方施法为空：页面显示「无候选施法」而非空白或报错。
- 同一技能 ID 在不同 Boss/小怪上下文出现：判定按「副本+Boss 上下文」维度存储，避免全局误伤。
- 判定清单尚未覆盖的技能：默认归入「未判定」组继续展示，不得凭空自动判定（文档明确「不从伤害或光环猜测缺失施法」）。
- 旧版 S1 样本（无判定数据）：完全不受影响，保持现有渲染。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1**: 系统必须为 S2 样本提供「副本+Boss 上下文」维度的关键技能判定数据文件，声明式、可版本化。
- **FR-2**: `/mythic-dungeon` S2 视图必须将候选施法分为：关键技能 / 小怪或其他 / 未判定，三组展示，未判定为默认。
- **FR-3**: 每条关键技能判定必须携带 evidence 结构（至少一类量化依据）。
- **FR-4**: 判定数据加载失败时必须优雅降级为现有「实际施法候选」行为，并给出可见提示；服务不得 5xx。
- **FR-5**: 判定数据文件必须与 S2 样本 JSON 一样不随代码提交（遵循 docs/mythic-dungeon-s2-samples.md 的维护口径），但在仓库内提供 schema 说明或示例供后续维护。
- **FR-6**: S1 既有样本与既有测试行为必须保持不变（回归基线）。
- **FR-7**: 前端选择器与通用运行时不得内嵌任何具体技能 ID 或判定规则（宪法原则 II）；判定逻辑仅存在于数据文件与 Boss/副本级插件层。

### Success Criteria

- 团长在 S2 页面 5 秒内能区分关键技能与小怪施法（分组清晰、无混排长列表）。
- 维护者新增/修订一条判定 ≤ 1 分钟（只改数据文件）。
- 全量 pytest 通过；S2 判定功能有专属测试覆盖分组、降级与上下文隔离三类场景。

### Assumptions

- 「关键技能」的首次判定来源：文档已记录的 S2 正式服机制认识 + 样本日志中敌方施法的量化证据，由维护流程人工确认后写入数据文件（本特性不实现自动判定算法）。
- S2 样本 JSON 仍由既有生成流程产出，本特性只消费其敌方施法数据。

## Key Entities

- **KeySkillRuling**: 判定条目 = { dungeon_zone, boss_context, spell_id, spell_name, category: key|trash|unreviewed, evidence: { metric, value, source }[] }。
- **S2 样本日志**: 既有四份正式服指定阵容样本（JSON，含敌方施法记录），判定数据的输入。
- **判定数据文件**: 声明式清单（JSON），按副本/Boss 组织，随 S2 样本同口径维护。
